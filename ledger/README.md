# The ledger

`observations.jsonl` — one JSON object per line, one line per (capability, version, run).

**Append-only.** Nothing edits a line that is already here. A capability that stops being true
does not get its old observation corrected; it gets a new one, and the disagreement between
them is the finding. The only write path other than append is `bedshock tidy`, which sorts the
file and alters nothing.

## A line

```json
{
  "capability": "item.max_durability.int16_ceiling",
  "version": "1.21.120",
  "api": "@minecraft/server 2.3.0",
  "platform": "bds",
  "method": "automated",
  "verdict": "YES",
  "measurement": { "samples": [{ "declared": 32768, "reports": -32768 }] },
  "evidence": "everything up to and including 32767 reports back exactly what was declared",
  "run": "bds-20260802T101500Z",
  "at": "2026-08-02T10:15:00Z"
}
```

| Field | |
|---|---|
| `capability` | Must resolve against `content/capabilities/`. `bedshock validate` fails on one that does not |
| `version` | The Minecraft version this was true on. The axis the whole repository exists to add |
| `platform` | `bds` · `client` · `imported` |
| `method` | `automated` · `observed` · `derived` |
| `verdict` | `YES` · `NO` · `INCONCLUSIVE` |
| `outcome` | For `observed` rows: which declared outcome was picked. Validated against the capability, including that its verdict matches |
| `measurement` | What the probe actually saw, structured. Not decoration — see below |
| `evidence` | One line from whoever or whatever recorded this |
| `note` | Free text, usually from a person. Never load-bearing, often the useful part |
| `run` | Groups every observation from one battery run |

## Why `measurement` matters

A verdict can hold steady across two runs while the numbers underneath it move. The durability
ceilings are the case in point: "every declared value reports itself" is a `YES` whether the
boundary sits at 32767 or somewhere else, and a change from *wrapping* to *clamping* would
leave both verdicts untouched while invalidating the design they were measured for.

So the rollup compares measurements as well as verdicts, and a same-verdict, different-numbers
disagreement at one version is `DRIFT`.

## `platform: "imported"`

Findings carried in from somewhere that was not this battery — in practice, the hand-maintained
document this repository grew out of.

These are real measurements and they are treated as such, but they carry a caveat their `note`
states: **the exact client build was not recorded at the time**, so the version on them is the
best available attribution rather than something anybody read off a screen. Every one of them
is replaced the first time the battery is actually run on a version.

Do not add new `imported` lines for anything you could have measured. The whole value of the
version axis is that a wrong column is worse than an empty one.

## Adding to it

You do not edit this file. `bedshock run` and `bedshock amend` append to it, and
`bedshock report` regenerates `docs/` from it.

The one exception is `bedshock collect <log>`, for a log captured somewhere this repository
could not reach — a CI artifact, someone else's machine. It goes through exactly the same
validation, including the refusal to record anything from a run that did not finish.
